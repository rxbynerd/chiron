# Pragmatic Internal Wire Formats for IIoT Data Normalization: A Comparative Analysis

## Executive Summary

Developing an Industrial Internet of Things (IIoT) startup that spans both legacy brownfield integrations and modern greenfield deployments requires an architecture that is highly resilient, mathematically precise, and agnostic to heterogeneous hardware. This report's primary recommendation is that Protocol Buffers (Protobuf) represents the most pragmatic serialization format for internal data normalization, offering the optimal balance of minimal payload size, broad language support, and strict schema enforcement. By standardizing raw southbound data—from register-based protocols like Modbus to frame-based networks like Controller Area Network (CAN)—into a unified internal stream of "metrics" and "events," disparate edge devices can ensure complete agreement on data types, byte ordering, scaling factors, and timestamps [cite: 1, 2].

Concerns regarding extreme resource constraints on greenfield microcontrollers (MCUs) are valid, but solvable. Utilizing the `nanopb` C library—distributed under the permissive zlib license (compatible with GPL) and available via the nanopb GitHub repository—allows Protobuf to operate securely within strictly allocated static memory [cite: 3, 4]. This entirely bypasses the dynamic memory allocation pitfalls that traditionally crash 32-bit MCUs with limited SRAM. To structure this payload, the overarching system should adopt the open-source Eclipse Sparkplug B `.proto` schema, governed under the Eclipse Public License 2.0 (EPL-2.0) via the Eclipse Foundation's Tahu project (available on GitHub and Maven Central) [cite: 5, 6].

Finally, while Sparkplug B natively leverages MQTT, constrained greenfield MCUs can bypass heavy TCP-based MQTT transport by transmitting the identical Protobuf schema over the lightweight Constrained Application Protocol (CoAP) running on User Datagram Protocol (UDP). The inherent security and reliability risks of connectionless UDP are directly mitigated by implementing Datagram Transport Layer Security (DTLS) for encryption and utilizing CoAP "Confirmable" messages to guarantee delivery without the overhead of persistent TCP sessions [cite: 7, 8, 9]. 

## Architectural Context and Data Normalization

Before selecting a wire format, it is critical to understand the demands of data normalization at the industrial edge. Heterogeneous southbound protocols provide raw, unstructured data. For instance, a Programmable Logic Controller (PLC) speaking Modbus might provide a temperature reading as a raw integer of `16742`, requiring the edge gateway to apply a scaling factor to yield `167.42°C` [cite: 1]. 

The core objective of data normalization is to establish a standardized data format across the entire system so that upstream applications—such as SCADA systems, historians, or predictive maintenance algorithms—can consume the data without requiring custom parsing logic for every sensor [cite: 2]. In legacy SCADA methodologies (such as those adhering to IEC 61131 standards), disparate protocol data is normalized into standardized database structures; if an incoming protocol lacks a timestamp, the gateway's information processor generates one to complete the internal structure [cite: 10]. 

To achieve this in a modern IIoT context, the internal wire format must support explicit typing (e.g., distinguishing between a 32-bit float and a 64-bit integer), precise timestamps, and metadata (such as engineering units) without causing payload bloat [cite: 2, 11]. The format must be split into two fundamental conceptual streams as identified in your query:
1.  **Metrics:** Continuous telemetry data, status flags, and process variables.
2.  **Events:** Discrete occurrences, alarms, and lifecycle state changes (e.g., device connection or disconnection).

## Serialization Formats: A Comparative Evaluation

The choice of serialization format dictates how data structures are encoded into byte streams for network transmission or memory storage. The landscape is broadly divided into two philosophies: schema-less formats and schema-driven formats.

Schema-less formats, such as JavaScript Object Notation (JSON), Concise Binary Object Representation (CBOR), and MessagePack, are self-describing. They embed field names (keys) directly alongside the values in every payload. Schema-driven formats, such as Protocol Buffers (Protobuf), FlatBuffers, and Apache Avro, rely on pre-compiled definitions shared between the publisher and subscriber, allowing the wire format to transmit only raw values and numeric field tags [cite: 12].

To understand the pragmatic implications of these formats, we must evaluate their performance characteristics across serialization speed, deserialization speed, and resulting payload size. 

The following table synthesizes strict benchmarking data derived from a Python 3.11.7 performance study consisting of 500 iterations against a single user-record payload [cite: 12].

| Serialization Format | Schema Type | Payload Size (Bytes) | Relative Size (vs JSON) | Serialization Speed | Deserialization Time (Total ms) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **JSON** | Schema-less (Text) | 513 | Baseline (0%) | 58,000 ops/s | 4.43 |
| **CBOR** | Schema-less (Binary)| 425 | -17.1% | 41,000 ops/s (12.19 ms total) | Omitted in source benchmark |
| **MessagePack**| Schema-less (Binary)| ~425 | -17.1% | 190,000 ops/s | Omitted in source benchmark |
| **FlatBuffers** | Schema-driven | Omitted in source benchmark | Larger than Protobuf | 68.18 ms total | **0.23** |
| **Protobuf** | Schema-driven | **279** | **-45.6%** | Omitted in source benchmark | 0.82 |

*Note: Specific baseline byte sizes fluctuate based on exact field implementation, but proportional reductions remain consistent across industry benchmarks [cite: 12, 13].*

The data reveals distinct trade-offs inherent in each format. JSON is universally supported but highly inefficient; a simple temperature reading represented as `{"sensorId":32,"sensorValue":24.5}` consumes approximately 36 bytes for a minuscule amount of actual data [cite: 14]. When scaling to thousands of tags per second, this verbosity causes severe network congestion [cite: 14].

MessagePack and CBOR optimize JSON by converting it into binary, achieving payload reductions of roughly 17.1% [cite: 12]. However, because they are schema-less, they still transmit field names as strings (e.g., the string `"rssi"` consumes 5 bytes in CBOR) [cite: 13]. In rigorous testing for Non-Terrestrial Networks (NTN) and constrained environments, CBOR and MessagePack payloads were found to be up to 88% larger than strict satellite constraints allow, disqualifying them for extreme low-bandwidth deployments [cite: 13].

FlatBuffers provides the fastest deserialization time (0.23 ms for 500 iterations) by utilizing a zero-copy memory layout—a concept analogous to reading a book directly from the library shelf without having to transcribe its contents onto your own notepad first—allowing applications to read data directly from the buffer without unpacking it [cite: 12, 15, 16]. However, it exacts a heavy cost on serialization speed (68.18 ms) and initial memory footprint, which can overwhelm constrained MCUs [cite: 12, 17]. Apache Avro, while popular in big data environments like Apache Kafka, lacks optional fields, meaning a default value must be transmitted even for unused data. Avro also requires a central schema registry to function properly, adding architectural complexity unsuitable for constrained edge devices [cite: 18, 19, 20].

Protocol Buffers (Protobuf) emerges as the clear victor for a unified internal wire format. By encoding data against a predefined `.proto` schema, field names are entirely omitted from the wire format, replacing them with minimal numeric tags [cite: 11, 12]. This results in payloads that are over 45% smaller than JSON [cite: 12, 21]. Furthermore, Protobuf is highly robust for long-term maintainability; it natively supports forward and backward schema evolution, allowing the startup to update data models without breaking legacy greenfield devices deployed years prior [cite: 12, 13, 15].

## Constrained Environments and Microcontroller Viability

Your query expressed valid concern regarding the viability of protocols like MQTT on constrained MCUs in greenfield deployments. The standard IT-centric implementations of Protobuf and MQTT rely heavily on dynamic memory allocation (`malloc()`) and extensive C++ runtimes, which are catastrophic for 32-bit MCUs with only tens of kilobytes of Static Random-Access Memory (SRAM) and Flash storage [cite: 22, 23].

### The Protobuf Implementation: Nanopb

To bridge the gap between high-level architectural standardization and low-level hardware constraints, the IIoT industry relies on `nanopb`. Nanopb is an ANSI C implementation of Protocol Buffers specifically designed for embedded systems and memory-restricted microcontrollers. It is distributed under the permissive zlib license (compatible with GPL) and available via the nanopb GitHub repository [cite: 3, 4, 24, 25]. 

Unlike the standard Google Protobuf compiler that generates heavy C++ classes, nanopb generates lightweight C structures [cite: 24]. Crucially, nanopb operates entirely without dynamic memory allocation; it utilizes statically allocated buffers determined at compile time [cite: 23]. If fixed-size fields or specific maximum string lengths are defined in the `.proto` schema using `(nanopb).max_size` options, the memory usage becomes perfectly predictable, ensuring execution safety in real-time operating systems (RTOS) [cite: 22, 26]. This nullifies the primary argument against using a rich schema on a constrained device, allowing edge sensors to serialize complex "metrics" directly into the overarching system format with minimal CPU and RAM overhead.

### Decoupling the Transport Protocol and Securing Connectionless Transport

While Protobuf solves the serialization constraint, the transport constraint (MQTT) must also be addressed. MQTT operates over the Transmission Control Protocol (TCP), which requires a persistent connection, sequence tracking, and a relatively heavy network stack. This can indeed cause battery drain and memory exhaustion on highly constrained MCUs.

A pragmatic architectural choice is to separate the *serialization format* from the *transport protocol*. Greenfield MCUs can utilize the exact same Protobuf schema as the rest of your architecture, but transmit the serialized binary payload over connectionless, lightweight protocols such as the User Datagram Protocol (UDP) or the Constrained Application Protocol (CoAP). Once these packets reach the local edge gateway (which acts as your normalization hub for brownfield protocols like Modbus and CAN), the gateway can easily ingest the payload and republish it over MQTT to the broader SCADA or cloud ecosystem.

If an architecture relies on connectionless CoAP over UDP to save resources on greenfield MCUs, it introduces an immediate logistical challenge: *How is data secured, and how is packet loss handled without TCP's inherent reliability?*

*   **Reliability via Confirmable Messages:** CoAP solves the UDP delivery problem by differentiating between 'non-confirmable' and 'confirmable' (CON) messages. By transmitting critical 'events' as confirmable messages, the greenfield MCU forces the receiving edge gateway to send an Acknowledgment (ACK). If the ACK is not received, CoAP natively handles the retransmission, preventing data loss on unreliable industrial networks [cite: 7, 8, 9].
*   **Security via DTLS:** To secure the payload over the wire, CoAP employs Datagram Transport Layer Security (DTLS). DTLS operates directly at the transport layer to provide symmetric encryption of the Protobuf payload, as well as mutual authentication using Pre-Shared Keys (PSK) or asymmetric Raw Public Keys (RPK). This ensures the strict confidentiality and integrity of the data, entirely mitigating the eavesdropping and tampering risks associated with raw UDP in an industrial environment [cite: 7, 8, 9, 27, 28].

## IIoT and SCADA Standardization Frameworks

Having established Protobuf as the optimal raw serialization format, the next pragmatic step is determining the structural schema. Rather than inventing an in-house schema—which invites long-term maintenance debt and isolates your startup from third-party interoperability—it is highly advantageous to adopt an open industrial standard. Three primary frameworks dominate the current IIoT and SCADA landscapes: SenML, OPC UA PubSub, and Sparkplug B.

### 1. SenML (RFC 8428)

The Sensor Measurement Lists (SenML) specification is an Internet Engineering Task Force (IETF) standard designed to represent simple sensor data [cite: 29, 30]. SenML organizes data into an array of records with standard abbreviated keys: `bn` (base name), `bt` (base time), `u` (unit), and `v` (value) [cite: 31, 32]. It typically encodes into JSON or CBOR [cite: 33]. 

While highly efficient for flat, simple sensor readings, SenML fundamentally lacks semantic depth [cite: 34]. It is poorly suited for complex, hierarchical data models or the rich event modeling required by a unified SCADA/IIoT pipeline [cite: 34]. Furthermore, because it relies heavily on CBOR or JSON, it suffers from the aforementioned schema-less payload bloat compared to Protobuf [cite: 12, 33].

### 2. OPC UA PubSub (UADP)

The Open Platform Communications Unified Architecture (OPC UA) is the heavy-duty standard of the industrial world. Historically operating on a client-server architecture, the OPC Foundation released Part 14 (PubSub) to address continuous sensor streaming [cite: 35, 36]. 

OPC UA PubSub offers two wire formats: JSON and the UA Data Protocol (UADP) [cite: 37, 38]. UADP is a highly compact, binary encoding optimized for bandwidth-constrained networks; a dataset message containing 50 variables fits into approximately 400 bytes [cite: 37]. Furthermore, UADP can be transmitted brokerlessly over UDP multicast [cite: 37, 39]. When combined with Time-Sensitive Networking (TSN) on Layer 2 Ethernet switches, OPC UA UADP allows for hard real-time, deterministic control loops with sub-5-millisecond latency [cite: 35, 37]. 

However, OPC UA is immensely complex. Adopting the OPC UA stack requires significant development overhead, and TSN-capable infrastructure remains expensive and relatively rare in older brownfield deployments [cite: 37].

### 3. Sparkplug B

Sparkplug B is an open-source specification managed by the Eclipse Foundation under the Eclipse Public License 2.0 (EPL-2.0). It standardizes how MQTT should be utilized in IIoT and SCADA environments [cite: 5, 6, 11, 40]. It directly resolves the issue that plain MQTT does not define topic structures or payload formats, which historically led to massive fragmentation and custom integration code for every device [cite: 11, 21, 41].

Sparkplug B specifically mandates the use of Protocol Buffers for all message payloads [cite: 21, 40, 41]. Its predefined, open-source `.proto` schema enforces strict typing for metrics (e.g., `Int32`, `Float`, `String`) alongside precise millisecond UTC timestamps and metadata (such as engineering units) [cite: 11, 42]. 

Crucially, Sparkplug B introduces structural paradigms highly beneficial to an IIoT startup:
*   **Device State Management:** It introduces "birth" (NBIRTH/DBIRTH) and "death" (NDEATH/DDEATH) certificates. When a device connects, it publishes a birth message containing its entire metric profile. If it disconnects, the MQTT broker automatically publishes a death certificate, alerting the SCADA system immediately [cite: 11, 41, 43].
*   **Report By Exception (RBE):** After the initial birth message, edge nodes only transmit data when a value changes. This functions much like a security guard who only radios headquarters when a door opens, rather than calling every five seconds to report the door is still closed. Industry data indicates that combining Protobuf's compression with RBE reduces total network bandwidth by 80% to 95% compared to standard MQTT JSON polling [cite: 14].
*   **Batching:** Multiple tag updates can be batched into a single Protobuf message, drastically reducing network chatter and broker overhead [cite: 21].

## Pragmatic Recommendation for the Internal Wire Format

Synthesizing the prior art, technological constraints, and your startup's dual-mandate of brownfield normalization and greenfield MCU support, the following architectural strategy is recommended:

**1. Adopt Protocol Buffers (Protobuf) as the Core Internal Wire Format.**
Protobuf provides the mathematically optimal intersection of speed, extreme payload reduction, and forward compatibility required for a unified data stream. It avoids the schema-less verbosity of JSON/CBOR and the complex registry requirements of Avro. 

**2. Leverage the Sparkplug B Schema (Without Being Bound to MQTT at the Extreme Edge).**
Instead of expending capital developing a proprietary in-house `.proto` schema to define "metrics" and "events," adopt the open-source Eclipse Sparkplug B `.proto` definition. It is natively designed for SCADA/IIoT, already models metrics flawlessly with distinct types and timestamps, and has robust ecosystem support [cite: 5, 6, 11, 42].

**3. Implement a Two-Tiered Transport Architecture.**
*   **Brownfield & Edge Gateways:** For robust equipment and edge gateways normalizing Modbus or CAN data, utilize full Sparkplug B over MQTT. This normalizes disparate machine protocols into a unified, SCADA-ready stream.
*   **Constrained Greenfield MCUs:** For battery-powered or memory-constrained MCUs, compile the Sparkplug B Protobuf schema using `nanopb` [cite: 3, 4, 24]. Instead of running a heavy TCP MQTT client on the MCU, transmit the resulting binary Protobuf payload securely via DTLS-encrypted CoAP Confirmable messages to your local edge gateway [cite: 7, 8, 9]. The gateway receives the CoAP packet, recognizes the pre-formatted Protobuf payload, and natively bridges it onto the main MQTT broker. This satisfies your requirement to bypass heavy transport protocols on MCUs while maintaining a perfectly homogeneous, secure, and reliable internal data stream from end to end.
