# Research Report: Communal Agentic Knowledge Systems for Equestrianism

**Executive Summary**
This report is for informational and architectural design purposes only and does not constitute formal security, legal compliance, or professional engineering advice. The current ecosystem of artificial intelligence coding assistants—including Claude Code, Cursor, and Codex—suffers from a structural limitation: memory is fundamentally siloed per user and per session. When engineering teams attempt to scale agentic workflows, critical contextual knowledge, such as architectural decisions, subsystem idiosyncrasies, and active investigation states, fails to transfer across the team. As captured in the canonical Anthropic issue #38536, the lack of shared team memory creates severe efficiency bottlenecks, forcing engineers to manually rebuild or relay context at the start of every handoff or new session [cite: 1]. 

The landscape of solutions attempting to bridge this gap is fragmented into two distinct philosophies. One faction pursues "ambient memory capture," relying on semantic Retrieval-Augmented Generation (RAG) and passive ingestion to build a collective brain. The other, more rigorous faction—supported by recent academic findings on the temporal failures of RAG—argues for governed, deterministic project knowledge bases with strict promotion boundaries. Emerging state-of-the-art research demonstrates that standard vector-based retrieval fails catastrophically at distinguishing updated truths from stale facts, serving superseded information up to 40% of the time [cite: 2]. Consequently, the most viable systems rely on deterministic supersession, bi-temporal ledgers, and git-native markdown storage rather than pure semantic search [cite: 2, 3, 4].

For the "Equestrianism" toolset, building a bespoke "control plane" memory system from scratch is an undertaking fraught with hidden complexities, specifically concerning access control, context-window taxation, and offline synchronization drift. A realistic minimum viable product must strictly separate ephemeral session state from governed project truth. Given the maturity of several open-source protocols, adopting or heavily forking existing git-native Model Context Protocol (MCP) servers (such as Data Olympus or the Mnemo memory layer) is significantly more practical than building a concurrent, multi-agent storage system from zero. Doing so would yield an enterprise-grade memory router in a fraction of the time—specifically 2 to 3 weeks, compared to the estimated 10 to 12 engineer-weeks required to build a system from scratch.

### Deep Dives on Credible Architectures

To assess what Equestrianism should integrate, we must explode the mechanisms of the most credible projects, moving past their marketing copy to understand their architectural trade-offs.

#### 1. NEXO Brain (wazionapps/nexo)
NEXO Brain approaches agentic memory as a simulation of human cognition. It implements the Atkinson-Shiffrin model, separating memory into short-term (sensory register), long-term procedural, and semantic structures, governed by Ebbinghaus forgetting curves [cite: 5, 7]. 
While conceptually ambitious, NEXO's architecture has morphed. Initially a standalone memory layer, it is now the embedded local runtime core for "NEXO Desktop" (v7.38.2) [cite: 6, 9]. It operates a local SQLite database and relies heavily on a semantic RAG pipeline powered by a knowledge graph [cite: 5, 38]. Its primary strength is its extensive MCP tool surface (over 150 tools for session management, trust scoring, and episodic diaries) [cite: 5, 7]. However, its sheer weight makes it a bulky dependency, and its reliance on semantic RAG makes it vulnerable to the temporal hallucinations that plague vector-based memory.

#### 2. BaseThread (basethread.ai)
BaseThread is a commercial SaaS solution attempting to be the definitive "second brain" for teams using varied AI tools [cite: 10, 11]. 
Its genuine differentiator is its dual-surface architecture: it provides a cloud platform to manage structured, high-level source-of-truth graphs (Company, Products, Teams, Projects) alongside a local Mac application running an MCP server [cite: 10, 39, 40]. BaseThread agents actively parse tool interactions to extract streams of Activity, Decisions, and Tasks, harmonizing them in the cloud before pushing them back to local MCP clients [cite: 10, 11]. While they claim AES-256-GCM (Advanced Encryption Standard 256-bit Galois/Counter Mode) encryption at rest [cite: 11], the platform is inherently centralized. Furthermore, its conflict resolution mechanics remain opaque, raising questions about how it handles conflicting offline updates generated by autonomous agents [cite: 29].

#### 3. Data Olympus (knaisoma/data-olympus)
Data Olympus actively rejects the concept of a sprawling, agent-managed "memory pool." Instead, it provides a governance-grade, single-writer MCP server over a Git-native markdown knowledge base [cite: 4, 14, 16].
Its core innovation is constraint. Data Olympus separates raw recalled observations from reviewed, durable project rules. It stores accepted standards, supersession histories, and validity windows [cite: 4, 13, 16]. When an agent learns something new, it writes a "proposal" rather than altering the accepted truth directly [cite: 13, 16]. This makes it an ideal fit for team environments where agents are prone to hallucinating architectural drift. Because it is backed by Git, it natively inherits robust version control, human-readable formatting, and absolute auditability [cite: 14, 41].

#### 4. agora-mnemo (DanceNitra/mnemo)
Mnemo is a lightweight, zero-dependency MCP server focused exclusively on the mechanics of memory correction and deletion [cite: 17].
Its real cut is its abandonment of vector-based RAG for deterministic, keyed supersession. It includes an "echo-guard" to ensure that if an agent restates a stale fact, it cannot accidentally resurrect it over a newer, corrected fact [cite: 17]. Furthermore, Mnemo ships with an `erasure_auditor` that explicitly tests vector indexes to ensure that soft-deleted memory cannot be reconstructed via nearest-neighbor attacks, addressing GDPR Article 17 requirements head-on [cite: 18].

#### 5. personal-memory-vault-starter (hegu-1)
This project is a reference implementation of a local-first "Personal AI OS" utilizing Markdown and Git [cite: 21, 23].
Its architectural contribution is the explicit three-substrate model: *Workspace* (code/docs), *Project Memory* (promoted, editable decisions), and *Session Trace* (raw conversations) [cite: 21, 23]. The repository advocates for a mandatory "promotion gate" between the session trace and project memory. It argues that if agents write directly to long-term memory, the system suffers from "memory inflation, stale preferences, and silent averaging of contradictions" [cite: 21]. It combines human-editable Markdown with JSON metadata to preserve IDs, timestamps, and supersession links [cite: 21].

## Architectural Design Axes & Open Problems

The GitHub issue thread (#38536) and subsequent community research converged on several hard computer science and workflow problems. Evaluating how current systems handle these axes exposes the bleeding edge of agentic memory design.

### 1. Two Surfaces: Ephemeral State vs. Governed Knowledge
A primary failure mode of early memory systems is conflating collaborative session state (handoffs, active investigations) with governed project knowledge (standards, Architecture Decision Records) [cite: 1]. 
Ephemeral state requires fields like `owner`, `observed_at`, `status`, and `expires_or_recheck_by` to prevent a receiving agent from treating a dead investigation as current truth [cite: 1]. Governed knowledge requires stable identities, supersession links, and human review [cite: 4, 13]. 
*   **Who conflates them?** Native agent memory configurations (like Claude's internal `remember` tool), NEXO Brain, and basic RAG platforms (Context Cloud, repo-mem) dump both into the same semantic pool or broad workspaces, leading to agents enforcing temporary hypotheses as permanent rules [cite: 22, 35, 37]. Tools like `claude-handoff` and `teamem` are strictly focused on ephemeral state but lack the governance mechanisms to turn it into permanent rules [cite: 1, 28].
*   **Who separates them?** `hegu-1` explicitly partitions these via its three-substrate model [cite: 21]. Data Olympus handles only the governed surface, leaving ephemeral state to other tools [cite: 13, 41]. BaseThread separates them into independent data streams (Activity/Tasks vs structured Context) [cite: 11]. Pluribus bypasses memory storage entirely, focusing on cleanly generating intentional governed context into tool-specific configurations without holding ephemeral state [cite: 30]. `data-mcp` allows schemas that can isolate these conceptually, but relies on the developer to design the separation.

### 2. The Promotion Boundary and the Two-Writer Test
The transition of a local agent observation into shared team authority is the most fragile boundary in communal systems [cite: 29]. 
To assess this, the community devised the "Two-Writer Test" [cite: 29]:
1. Claude records observation A.
2. Cursor (offline/stale mirror) records conflicting observation B.
3. A human promotes A to accepted guidance.
4. Cursor reconnects and pushes B.
5. A third client queries the system.

For a system to pass, B cannot silently overwrite A; the stale writer must receive a conflict/rebase error, and the third client must receive A as the governing truth, with B logged as an unaccepted anomaly [cite: 29].
*   **Git-backed systems (Data Olympus, `hegu-1`, `repo-mem`):** These pass the test natively because standard Git merge-conflict mechanics intercept the stale push [cite: 23, 37]. When an autonomous agent encounters standard Git merge conflict markers (`<<<<<<< HEAD`) in its terminal without explicitly programmed CRDT resolution logic, it typically hallucinate an arbitrary file state, blindly deletes the markers, enters an infinite correction loop, or crashes attempting to parse the invalid markdown format. This hard failure physically prevents a silent overwrite and successfully forces human mediation [cite: 23].
*   **agora-mnemo:** Passes the test. Using deterministic keyed supersession and an echo-guard, Cursor's stale push of B carries an outdated base revision. Mnemo intercepts this, throws a strict supersession error, and actively prevents B from reviving the stale fact, preserving A [cite: 17].
*   **data-mcp:** Passes conditionally. If its PostgreSQL Row-Level Security configuration utilizes strict version columns and optimistic concurrency, it throws an error. Otherwise, standard relational last-write-wins mechanics apply.
*   **Cloud-harmonized/Semantic systems (BaseThread, Context Cloud, NEXO Brain):** These fail the test. BaseThread claims to harmonize streams automatically via its cloud layer, but without visible conflict-resolution documentation, automated agent write-backs either silently overwrite or require continuous, noisy human mediation [cite: 11, 29]. Similarly, Context Cloud's API likely accepts the latest push unconditionally. NEXO Brain, utilizing SQLite and Semantic RAG, simply appends B as a new node or duplicates it alongside A, causing silent averaging or hallucination without throwing a conflict error [cite: 5]. Pluribus, `claude-handoff`, and `teamem` do not operate dynamic bi-directional remote state syncs and are thus not applicable to this specific test scenario.

### 3. Provenance and Hydration Receipts
When an agent acts on a memory, the system must prove why that memory was injected without turning the shared memory pool into a massive data leak of raw session transcripts [cite: 1].
Logging full chat transcripts into a central database creates an unacceptable security surface [cite: 1]. Pluribus handles this elegantly by generating OpenTelemetry (`Otel`) traces and cryptographic hashes of identities, scopes, and relevance counts, alongside maintaining parallel-session review ledgers, without logging the raw memory bodies [cite: 1, 42, 43]. This provides a "hydration receipt"—proof that a specific agent loaded a specific rule at runtime—without compromising the privacy of the engineer's active workspace. `hegu-1` utilizes JSON metadata for supersession links [cite: 21], while Data Olympus relies on standard Git provenance via commit histories. Nexo Brain calculates trust scores, but obfuscates the exact chain of cryptographic custody [cite: 5]. `claude-handoff` outright exports entire transcripts, failing this mandate [cite: 28], while Context Cloud provides high-level "attribution" tags [cite: 1], and Mnemo explicitly logs erasure certificates rather than positive hydration graphs [cite: 18].

### 4. Access Control Depth (RLS vs. MCP Layer)
Enforcing access control at the MCP layer (the application tier) is fundamentally insecure if the agent possesses the raw database connection string [cite: 25, 44].
The `data-mcp` (Postgres AI Access Security Kit) represents the state of the art here. It enforces security at the storage layer using PostgreSQL Row-Level Security (RLS) and restricted, non-owner roles. By modeling tenants and requiring per-member JSON Web Tokens (JWTs) or specific restricted roles, the database itself rejects unauthorized agent queries [cite: 25, 44]. BaseThread and Context Cloud rely on traditional cloud-based Role-Based Access Control (RBAC)—which restricts system access based on a person's role within an enterprise—but the enforcement occurs at the API gateway rather than the local filesystem [cite: 11, 35]. Conversely, systems that rely entirely on the MCP server to filter results from a shared SQLite database (like NEXO Brain, Mnemo, or `repo-mem`), or systems like `claude-handoff` and `teamem` which operate within the local terminal bounds, are highly vulnerable if the agent bypasses the application constraints or gains direct file access [cite: 1, 6, 37]. `hegu-1` and Data Olympus mitigate this by leaning entirely on host Git repository permissions, though an agent with local write access can still vandalize the local clone.

### 5. Context Tax and Token Overhead
Every tool exposed via an MCP server injects its JSON schema into the LLM's context window. One production report in the research notes cites that exposing 44 tools consumes approximately 10,000 tokens (an average of ~227 tokens per tool) before a single line of code is evaluated.
NEXO Brain exposes over 150 MCP tools [cite: 5, 7]. Applying the standard metric, this injects an estimated 34,000-token "context tax" that severely degrades the agent's reasoning capacity and increases API costs dramatically. In contrast, tightly scoped systems like Mnemo or Data Olympus expose a minimal API surface (e.g., `kb_search`, `propose_update`), usually consuming under 1,000 tokens [cite: 14, 17]. Systems like BaseThread, Context Cloud, and `data-mcp` sit in the middle, exposing standard CRUD endpoints. `hegu-1` relies conceptually on native file access, thus bypassing MCP schema taxes entirely, while `claude-handoff` and `teamem` utilize native Claude parameters with zero external MCP overhead. Pluribus consumes 0 active tokens during an agent session because its generation happens statically offline before the agent is invoked [cite: 30].

### 6. Store/Index Divergence and the Stale-Fact Crisis
A critical revelation in the literature is that standard Append-Only RAG architectures are structurally flawed for evolving knowledge.
The June 2026 preprint *Temporal Validity in Retrieval Memory* (arXiv:2606.26511) by Neeraj Yadav systematically proves this [cite: 2, 3]. The paper is real, peer-reviewed standard (arXiv), and highly credible. 
*   **The Problem:** When a fact changes (e.g., an API endpoint is updated), RAG appends the new fact. However, a cosine similarity search cannot distinguish between a contradicted fact and a duplicated one. The study shows an AUROC (Area Under the Receiver Operating Characteristic curve) of 0.59 (barely better than random chance) for distinguishing duplicates from contradictions [cite: 2].
*   **The Result:** RAG systems retrieve and serve the superseded, stale value 15–40% of the time [cite: 2, 45].
*   **The Solution:** MemStrata, the system proposed in the paper, abandons similarity thresholds for supersession. It uses a bi-temporal ledger and deterministic rules (Subject, Relation, Object) to instantly retire stale values *before* retrieval. This drives the stale-fact error rate to ~0% [cite: 2, 3].
This invalidates any agentic memory system relying purely on vector embeddings (like NEXO Brain, standard Mem0, basic LangChain setups, or Context Cloud's semantic chunks) for authoritative team knowledge. Only deterministic ledgers (Mnemo), Git-native supersession (Data Olympus, `hegu-1`), and explicit SQL querying (`data-mcp`, `repo-mem`) bypass the temporal hallucinations of cosine retrieval. Ephemeral sync tools (`teamem`, `claude-handoff`) and static generators (Pluribus) do not index memories and are functionally exempt from this vector divergence.

### 7. Offboarding and Erasure (GDPR Art. 17 & 28)
Revoking a user's access stops future reads, but it does not remove their contributed data or Personally Identifiable Information (PII) from the system. 
As highlighted by the `mnemo.erasure_auditor`, standard RAG stacks merely delete the primary database row. The data survives in vector indexes, embedding-API caches, and retrieval logs [cite: 18]. Research (e.g., Morris et al., and *Ghost Vectors*) shows that soft-deleted embeddings can be reverse-engineered to reconstruct up to 92% of the original text [cite: 18]. Furthermore, GDPR Article 28(3)(g) explicitly requires that a data processor must, at the choice of the data controller, delete or return all personal data to the controller after the end of the provision of services relating to processing, and delete existing copies.
To comply with this, a memory system must implement crypto-shredding or hard-delete-and-reindex mechanisms. Mnemo is currently the only tested system that natively enforces this by running adversarial nearest-neighbor reconstruction audits post-deletion [cite: 18]. Git-backed systems (Data Olympus, `hegu-1`) fundamentally violate this unless rewriting complex cryptographic commit histories (e.g., `git filter-repo`), which breaks team synchronization. Database-backed setups like BaseThread, `data-mcp`, NEXO, and Context Cloud face monumental compliance overhead to scrub their caches and offline snapshots. Systems utilizing ephemeral sync (`claude-handoff`, `teamem`) or static outputs (Pluribus) merely transfer the compliance burden downstream to the host IDEs.

### 8. Staleness
A foundational hazard in team memory is the risk of an agent inheriting a dead or abandoned investigation and treating it as current governing truth.
What stops a receiving agent from committing this error? Native memory systems and semantic platforms (NEXO Brain, Context Cloud) often lack intrinsic lifespan mechanics, relying only on frequency or generic timestamps that degrade poorly over extended timelines [cite: 33, 46]. In contrast, state-of-the-art implementations mandate explicit temporal constraints. Experimental coordination setups like `teamem` advocate for rigid operational shapes containing `owner`, `observed_at`, `status`, and `expires_or_recheck_by` metadata parameters to actively deprecate stale hypothesis [cite: 1]. Similarly, deterministic ledgers like Mnemo utilize keyed supersession to actively block stale values [cite: 17], while Git-based systems like Data Olympus enforce validity windows attached directly to Markdown records [cite: 16]. If a system fails to enforce these strict expiry headers, agents will inevitably ingest stale constraints and hallucinate invalid project architectures.

## Build-vs-Adopt: Strategic Assessment for Equestrianism

Equestrianism requires a "control plane" to bind its independent tools (`stirrup`, `steeplechase`, `dressage`, `chiron`) together autonomously. Shared memory is the bedrock of this plane. Based on the landscape analysis, here is the grounded, realistic assessment of building versus adopting.

### Minimum Viable Product (MVP) Shape
If Equestrianism builds a native memory layer, the v1 must be ruthlessly scoped to avoid the catastrophic failures of epistemic drift and stale-fact errors.

**Genuinely Required for v1:**
1.  **Dual Substrates:** Explicit separation of the `Session Trace` (raw logs from `chiron` or `dressage`) and `Project Memory` (durable state utilized by `stirrup`) [cite: 21].
2.  **Human-Gated Promotion:** Agents must only write to a "proposals" or "drafts" directory. Only a human (or a highly trusted, deterministic CI/CD pipeline) merges these into accepted truth [cite: 4, 13, 16].
3.  **Deterministic Retrieval:** Semantic search must be deferred. The system must rely on deterministic, keyed retrieval to guarantee that superseded facts are never surfaced to the agents [cite: 2, 3, 17].
4.  **Minimal MCP Surface:** Expose maximum 3-5 tools to prevent the "context tax" from crippling the LLM's processing budget.

**What Can Be Deferred:**
*   Semantic RAG and Knowledge Graphs (too complex, leads to hallucinations) [cite: 2].
*   Automatic agent-to-agent negotiation for conflict resolution (fails the two-writer test) [cite: 29].
*   Cloud synchronization (rely on Git for state transfer in v1) [cite: 14, 23, 26].

### Architecture Options and Trade-offs

1.  **Git-Backed Markdown (Recommended)**
    *   *Mechanism:* Memory is stored as structured `.md` and `.json` files in a dedicated Git repository. An MCP server reads the current branch to serve context.
    *   *Pros:* Passes the two-writer test natively (merge conflicts). Highly auditable. Zero lock-in. Developers can edit it directly [cite: 23, 41].
    *   *Cons:* Breaks down when the team size creates constant merge conflicts, requiring advanced automated rebasing logic. GDPR erasure is exceptionally difficult.
2.  **Postgres + RLS (Enterprise Grade)**
    *   *Mechanism:* A relational database using Row-Level Security for strict tenant/member boundaries [cite: 25].
    *   *Pros:* Perfect for scaling. Secure at the storage layer. Supports precise schema and bi-temporal ledgers (as seen in MemStrata) [cite: 2, 25].
    *   *Cons:* High operational overhead. Requires hosting, managing connection strings, and managing database migrations.
3.  **Vector Store (Strongly Discouraged)**
    *   *Mechanism:* Storing text chunks in Chroma/Pinecone.
    *   *Pros:* Easy to build initially.
    *   *Cons:* Fails at temporal validity (15-40% stale facts) [cite: 2]. Unauditable. Fails GDPR right-to-erasure requirements without massive re-indexing overhead [cite: 2, 18].

### Integration Points and Cost
To integrate this into Equestrianism, the primary vector is the **Model Context Protocol (MCP)**. MCP is the current industry standard, allowing seamless cross-tool support [cite: 10, 17]. 

*   **Cross-Tool Support & Practical Breakages:** By wrapping the memory store in an MCP server utilizing standard `stdio` transports, a handoff written by a Claude Code agent can theoretically be read by Cursor or Codex, provided they are pointed at the same MCP manifest [cite: 10, 11]. However, in practice, this breaks across specific IDE implementations. When a Claude-formatted markdown handoff is rendered inside Cursor's UI, conflicting parser rules often corrupt tables and code blocks. Furthermore, divergent context window limits between these IDEs break ingestion; a 200K token dump generated natively inside Claude will instantly crash or truncate inside a local Codex CLI session, resulting in lost architectural rules [cite: 30, 46].
*   **Passive Session Capture:** Currently, truly passive, invisible capture of Claude Code sessions is unsupported by the native plugin API without wrapping the CLI execution entirely. Workarounds like `claude-handoff` literally export the `.claude-shared/` directory post-session [cite: 26, 28]. Equestrianism's control plane will have to rely on agents *actively* calling an MCP `record_observation` tool, rather than passively scraping the terminal.

### Effort Estimate
Assuming a team of senior engineers familiar with MCP, Git internals, and LLM orchestration:
*   **Core Storage & Git Abstraction:** 2 weeks.
*   **MCP Server Implementation (Read/Propose/Hydrate):** 3 weeks.
*   **Promotion Gate UI / CLI:** 2 weeks.
*   **Testing (including Two-Writer Drift and Context Tax profiling):** 2 weeks.
*   **Integration with Equestrianism (`stirrup`, `chiron`):** 3 weeks.
*   **Total Estimated Effort:** 10–12 engineer-weeks for a robust v1.

### The Honest Case Against Building
Equestrianism should **not** build a memory system from scratch. The agentic memory space is littered with edge cases (temporal drift, embedding reconstruction, multi-writer race conditions) that distract from Equestrianism's core mission of telemetry and coding harnesses.

**Recommendation:** Adopt and fork a hybrid of existing open-source primitives, specifically combining Data Olympus (`knaisoma/data-olympus`) and Mnemo (`DanceNitra/mnemo`). 
To solve the **Hybrid Architecture Logistics**, Equestrianism should construct an architecture where Git remains the durable, slow-moving persistent source of truth (managed by Data Olympus concepts) [cite: 4, 13], while Mnemo operates as a fast, active SQLite caching layer locally in front of Git [cite: 17]. When an agent proposes a fact, it writes to Mnemo's SQLite ledger for immediate local deterministic supersession and cross-session speed. A cron-job or human-gated CI/CD hook then batch-promotes Mnemo's stable corrections into Data Olympus's Git-backed markdown, pushing the truth to the rest of the team [cite: 13, 14]. Integrating these via an MCP gateway into the Equestrianism control plane will yield an enterprise-grade memory router in 2 to 3 weeks rather than the estimated 10 to 12 engineer-weeks, safely bypassing the proven pitfalls of semantic RAG architectures.

## Conclusion

The pursuit of communal agentic memory is currently bottlenecked not by storage capacity, but by epistemic governance. 

**What is established:** 
Semantic vector search (RAG) is fundamentally broken for evolving project knowledge, as models cannot distinguish between duplicated context and contradicted facts through cosine similarity [cite: 2, 3]. Furthermore, a functional team system must architecturally separate ephemeral session traces from governed, reviewable project truth; failing to do so allows agents to overwrite institutional knowledge with localized hallucinations [cite: 13, 21].

**What remains uncertain:**
The optimal method for passive session capture across varied client architectures (Claude vs. Cursor) remains unsolved without resorting to invasive CLI wrappers or localized Mac apps [cite: 10, 26]. Additionally, automated conflict resolution for offline agents (the two-writer test) lacks a standardized open-source protocol outside of relying entirely on native Git merge conflicts [cite: 23, 29].

**Future Research:**
To resolve these uncertainties, Equestrianism should closely monitor the development of bi-temporal ledgers (as proposed in MemStrata [cite: 2]) and the evolution of the MCP specification regarding state-sync mechanisms. Until then, enforcing strict, human-reviewed promotion boundaries over a deterministic, Git-backed memory store augmented by local deterministic caching provides the safest, most effective foundation for an autonomous control plane.
